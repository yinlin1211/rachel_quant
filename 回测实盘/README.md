# 回测实盘：数据读取加速与撮合复用

> 目标：在不损失 tick 级精度的前提下，把全年回测从 **11.3 小时** 压到 **3 小时以内**，
> 并复用已有的 C++ 撮合引擎，避免重复造订单簿。
>
> 本文所有数字都是实测，不是估算（标注「估算」的除外）。

---

## 1. 一句话结论

**不需要压缩数据。** 文件本身已经带索引，改用「按索引读 + 三路归并」就能快 3.7 倍；
压缩只是可选的第二步（再省 38%），不是提速的前提。

| 方案 | 单日 | 全年 237 天 | 额外磁盘 |
|---|---|---|---|
| 现状（顺序扫 + 全量排序） | 172 秒 | 11.3 小时 | — |
| **改读取器（按索引 + 归并）** | **47 秒** | **3.1 小时** | **0** |
| 再叠加字段级压缩（可选） | ~30 秒 | ~1.9 小时 | ~2.4 TB |

## 3. TickPool 文件格式（实测解析）

### 3.1 六段式结构

```
+0x00  int64   总条数 436,852,698        ← 注意：不是 magic
+0x08  int64   channel 数 5,213（= 股票数）
+0x10  5 × int64  五张 per-channel 描述符表偏移，间隔恒为 41,745,704 = 5213 × 8008
+0x38  int64   didx 索引区偏移
```

| 段 | 大小 | 内容 |
|---|---|---|
| 描述符表 ×5 | 各 41.7 MB | 每股票 8008 B：1000 个 8B chunk 指针 + 4B 条数 |
| chunk 指针区 | — | 每 **4096 条**一个指针，可直接跳转 |
| didx 索引 | 3.5 GB | 每条 tick 一个 8 字节条目 |
| 记录区 | 16.0 GB | 定长记录：MD 256B、TS 32B、OD 20B |

**真正需要读的是 19.5 GB（didx + 记录区），不是 23.9 GB。**

### 3.2 记录构成（20260105 全天）

| 类型 | 条数 | 占比 |
|---|---|---|
| MD 行情快照 | 21,470,995 | 4.9% |
| TS 逐笔成交 | 186,411,462 | 42.7% |
| OD 逐笔委托 | 228,828,545 | 52.4% |
| 其他（type=4，29 只无数据股票） | 141,696 | 0.03% |

### 3.3 关键性质：每只股票的三类子流本来就是时间有序

> 抽样 1,738 个 channel、1.53 亿条记录：
> md 倒序 **0** 次、ts 倒序 **0** 次、od 仅 67 次（均为 10 ms）
> 记录偏移递增违例 **0** 次

**结论：不需要任何排序。** 我们现在的「分桶 + 桶内排序」是多余动作。

### 3.4 磁盘特性

| 测量 | 结果 |
|---|---|
| 单流顺序读（O_DIRECT） | 530~555 MB/s |
| **4 路并发** | **245 MB/s（反而更慢）** |
| 页缓存命中 | 2.7~4.3 GB/s |

**并发不扩展**，因为 `/opt` 是单块 ext4（`/dev/sdb`）。多进程只会互相拖慢。

## 4. 加速方案（不改数据）

### 4.1 读取流程

```
① 解析 64 字节文件头 → 拿到 5 张描述符表偏移
② 对每只股票 c：读它的描述符 → 得到 md/ts/od 各自的 chunk 链
③ 三条链各自已有序 → 三路归并（三个游标向前走，零排序）
④ 边读边算分钟聚合（OHLC、成交量、盘口），不落地原始 tick
⑤ 截面部分在内存里做（5213 × 240 根 bar ≈ 50 MB）
⑥ 只对被选中的 ~20 只股票，按需回读它们的 tick 做撮合（几 MB）
```

### 4.2 为什么快

| 项 | 现状 | 改后 |
|---|---|---|
| 读取量 | 23.9 GB | 19.5 GB（少 18%） |
| 排序 | 4.37 亿条全量排序 | **0** |
| 并行 | 单线程 | 按股票切分（受磁盘限制，4 路即饱和） |
| 实测 | 172 秒 | **46.7 秒** |

### 4.3 必做的验证

格式是探测反推的，**必须先对账**：

```
新读法生成 20260105 的分钟 bar
  → 与现有 pipeline/panels/20260105.panel 逐值比对
  → 完全一致才算读法正确
```

不一致说明 chunk 指针或记录布局理解有误，退回探测阶段。

## 5. 压缩：可选，不是必须

| 结论 | 实测 |
|---|---|
| 整条记录去重 | **无效**：MD 十档全同仅 1.25~2.84%，TS/OD 为 0% |
| 字段级 delta（MD） | 每条平均只有 7.1/40 个档位变化 → 256B 可压到 **55B（-78.6%）** |
| TS | 撤单占 17.3%，4 个标志字节仅 3 种取值 → 省 18% |
| OD | 撤单 11.3%，2 字节恒零 → 省 15% |
| 合计 | 16.04 GB → **9.96 GB（-38%）** |

**建议：先做第 4 节的读法改造，压缩留到确实需要省磁盘或再要 1.5 倍时再做。**
理由：压缩要重写约 2.4 TB 数据，而读法改造是零磁盘成本。

## 6. 撮合：建议直接复用 bt5，不要自研

### 6.1 他们的引擎

`liblf_bt5.so` 符号可见：

```
OrderBookMgr::on_data_od / on_data_ts
ShBook::on_od / SzBook::on_od          ← 沪深两套订单簿
lfquant::quant_backtrace_base
lfquant::default_backtrace / orderbook_backtrace
```

策略接口（`lf_quant_backtrace_base.h`）：

```cpp
class quant_backtrace_base {
    virtual bool init(const lf_basket&) = 0;
    virtual void on_request(const lquant_order_t&);          // 下单
    virtual void on_tick(lquant_tick_pool*, int didx, const std::string&) = 0;
    virtual int calc() = 0;
};
```

**待实测**：`--cuoheType` 的 4 个取值分别对应哪种撮合模型（其中应有按订单号的模型）。

### 6.2 我们自研的现状（`pipeline/src/sim_live.cpp`）

八个组件都已实现并跑通：逐 tick 回放、订单生命周期、撮合、账户（T+1）、费用、
流式因子、风控、成交日志。

**但 L3 精确重建还没做成**：

| 映射假设 | L1 匹配 | 全十档精确 | 量误差 |
|---|---|---|---|
| add=`A`, cancel=`D` | 27.3% | 5.6% | 22.0% |
| add=`0`, cancel=`D` | 13.8% | 0% | 36.9% |
| **add=`0`+`A`, cancel=`D`** | **40.1%** | **5.1%** | **31.3%** |

**离「精确」还很远。** 与其继续反推格式，不如直接用 bt5 的订单簿实现。

### 6.3 已确认的字段语义（实测）

```
OD nType:  '0' 60.0%   'A' 28.5%   'D' 11.3%   '1' 0.16%   'U'/'S' 少量
TS fc:     '0' 成交    'C' 撤单（nPrice=0，带订单号）
TS 84% 的成交同时带买卖双方订单号
OD 100% 带订单号
```

### 7.1 因子研究（16 轮，约 1,800 个候选）

| 结论 | 数值 |

|---|---|

## 8. 建议的实施顺序

```
第 1 步  ★  改读取器：按描述符表 + chunk 指针 + 三路归并
           验证：分钟 bar 与现有 panel 逐值一致
           收益：172 秒 → 47 秒/天，全年 11.3h → 3.1h，零磁盘成本

第 2 步  ★  实测 bt5 的 4 种撮合模型
           用 t0_base_RF 示例跑一天，确认 cuoheType 语义与成本口径
           收益：省掉自研订单簿（原估 2~4 周）

第 3 步      把我们的因子/策略接进 bt5 的策略基类
           保留我们的数据层与因子流水线

第 4 步（可选）字段级压缩
           收益：再省 38% 读取量、约 1.9 小时/年
           成本：重写约 2.4 TB 数据
```

## 9. 风险清单

| 风险 | 影响 | 缓解 |
|---|---|---|
| 格式靠反推，chunk 指针语义未 100% 确认 | 读法可能出错 | 第 1 步必须做 bar 对账 |
| bt5 的成本模型未知 | 回测口径可能与我们的不一致 | 用它自己的成交明细核算手续费与滑点 |
| bt5 闭源 | 无法修改撮合逻辑 | 只把它当撮合器，策略与风控在外层 |
| 磁盘并发不扩展 | 全年最低约 3 小时 | 接受；或上 NVMe |
| L3 重建未达标（40%） | 做市模拟不可信 | 改用 bt5 的 ShBook/SzBook |
| 20 天样本 | 策略结论不稳 | 扩到 60 天/全年 |
